How we work

The process is short and written down. You know what gets delivered, and when, from the start.

  1. Conversation

    We start with a short call: the problem, the user, the constraints and what you already have. No pricing at this stage; I want to understand the work first.

  2. Scope and proposal

    A written scope: what's in, what's out, and by when. The price is project-based and fixed. If the scope changes, both are updated in writing.

  3. Development

    Short cycles: a working build and a short note every week. You have access to the repository, so you never have to guess at progress.

  4. Delivery and handover

    Signed build, source code, accounts and a handover note. Maintenance is a separate agreement; it is not required.

Approach

How I build

Saying it works is not enough; show how it was verified.

  1. Architecture

    I keep logic apart from shells like Android, the network and the disk: pure classes, hand-wired dependency injection, one network exit. That is how RideDeck's GPS filter and crash detection, and Aile Cüzdanı's service layer, are tested without a device.

  2. Testing

    Unit tests, type checks and lint run on every change. Aile Cüzdanı also has HTTP-level integration checks against a real PocketBase instance. RideDeck's CI runs tests, lint and an R8-minified release build. I do not describe something as field-tested when it is not.

  3. Privacy

    Data that does not need to be collected is not collected: RideDeck has no account or server, EXIF Cleaner and Sohbet Özeti are locked off the network by a content security policy. In Aile Cüzdanı personal data is kept only so the product can work.

  4. Security

    Authorization is decided on the server, not the client: access rules, role checks, rate limiting. Secrets and private source never enter public repositories; tests never write to the live database.

  5. Deployment

    Changes move in small commits. Mobile builds ship signed on GitHub Releases; this site is served from my own server with Caddy. Database changes are append-only migration files, and every step that touches a live system has a way back.

Frequently asked questions

If you have something else in mind, write to me.

How long does a project take?

It depends on scope; the start and delivery dates are written into the proposal. A single screen and a store release do not take the same time. I clarify the scope before I give a date.

How is pricing set?

A fixed, project-based quote. We agree the scope together; anything outside it becomes a separate quote. I do not work by the hour.

Who owns the source code and accounts?

You do, at handover. Store accounts are opened in your name and my access ends when the project is delivered. On open-source projects the licence is already on the project page.

Do you work remotely?

I work remotely from Istanbul and am used to running projects remotely. An in-person meeting can be arranged when it helps.

Confidentiality and NDAs?

I sign NDAs. Client code and data never go into public repositories; screenshots and write-ups use demo data.

Do you take small jobs?

Yes, when the scope is clear: one bug, one screen, one store release. If the scope is vague, we start with a short call.

Do you provide maintenance?

After delivery, maintenance runs under a separate agreement and is not required. If you prefer, you take the code and the handover note and continue with your own team.
